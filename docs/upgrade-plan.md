# mathmodel-kit 定位升级方案：从技能集到开放的数模工具箱

> 版本：v1.1.0 ｜ 状态：首期已落地 ｜ 英文版：[upgrade-plan_EN.md](upgrade-plan_EN.md)

本文回答一个问题：**mathmodel-kit 如何从「一套提示词为中心的 agent 技能集」升级为「开放的、可合作的数模工具箱」**。
全文结论都尽量绑定仓库中的真实文件与行号，未经验证的推断会显式标注。

---

## 一、定位诊断：差距在哪

当前形态是**以提示词为核心、以少量 CLI 脚本为落地件**的技能集：`math-modeling-helper` 是纯规范编排器（无代码），
`mathmodel-figure`（20 个数据图表模板）、`mathmodel-diagram`（5 个 JSON 驱动示意图模板）、`mathmodel-paper`
（LaTeX/Word 流水线 + 零宽字符清理）是三个专项落地件。

「工具箱」要求的不是更多功能，而是**可被他人依赖的契约**。差距按层拆分如下：

| 层次 | 「技能集」现状 | 「工具箱」要求 | 首期处置 |
|---|---|---|---|
| 契约层 | 模板信息以硬编码字典、docstring、人工文档三处存在，无机器可读 Schema | 单一事实源 + 机器可读数据契约 | 已落地：两侧 `manifest.json` + 5 份 JSON Schema |
| 样式层 | 配色写死在 `plot_style.py` 常量与其余模板脚本头部，只有「改源码」一条路 | 配色成为可声明、可替换、可校验的数据 | 已落地：`themes/theme.schema.json` + 默认主题 + `--theme` / `validate_theme.py` |
| 接口层 | 8 条 CLI，参数风格各异；示意图无统一入口、无 `--list` | 稳定的命令行契约 + 可枚举、可校验、可退出码判定的接口 | 已落地：统一 CLI、`--list --json`、`validate_content.py` |
| 治理层 | 无 CONTRIBUTING、无版本号、无 CHANGELOG、无发布流程 | 贡献流程、评审口径、语义化版本、发布自动化 | 已落地：CONTRIBUTING×2、PR/Issue 模板、`VERSION`、`CHANGELOG.md`、`release.yml` |
| 生态层 | 仅示范 Claude Code 的安装方式；无对外索引 | 多宿主分发、可被第三方发现与引用 | 部分落地：见 §11 Phase 2 |

关键判断：**瓶颈不是缺功能，而是缺「别人能依赖的东西」**。因此首期没有新增任何建模能力，全部投入契约与治理。

## 二、可行性分析

### 2.1 技术可行性：增量式，无破坏性改造

首期全部改动都是**叠加**而非重构，并有机器验收：

- 数据图表渲染器的三张硬编码字典迁入 `skills/mathmodel-figure/code/tools/manifest.json` 后，
  `--list` 输出与别名/中文解析行为与迁移前**逐项一致**（81 个解析用例 + 20 个 id 全等，0 失败）；
- 示意图原有的逐模板调用 `python3 code/templates/problem_flow.py content.json -o out.png` **保持可用**，
  统一入口只是在其之上补了枚举与解析；
- 模板脚本、产物路径、产物格式（PNG 300 DPI + 矢量 PDF/SVG）一律未变。

即：**开放化不以破坏既有用户为代价**，这是可行的前提。

### 2.2 生态可行性

- 许可已就绪：Apache-2.0（[LICENSE](../../LICENSE)），允许商用与二次分发，是第三方敢于依赖的前提；
- 质量门禁已就绪：CI 覆盖语法、模板渲染、Schema 校验、注册表一致性、LaTeX 编译，贡献者可自助验证；
- 发现渠道已存在：社区已出现专门收录此类项目的公开目录（32 个项目、固定 commit 与 SHA-256 校验），
  说明「可复现、许可证清晰、人机边界明确」正是被评估的维度——与本项目的既有取向吻合；
- 需求侧真实：数学建模赛事的 AI 辅助已是活跃赛道（见 §10），不必教育市场。

### 2.3 成本可行性

本项目**无服务端、无数据库、无运维、无 API 配额**：全部产物是文件与 CLI，运行在用户自己的 agent 宿主与本地 TeX/Python 环境中。
边际成本主要是评审人力，属于可被 §7 流程与 §8 激励摊销的部分。

### 2.4 不可行或暂不做的部分

| 事项 | 判断 | 理由 |
|---|---|---|
| pip 包化 / 发布到 PyPI | **暂不做** | 技能以目录分发，包化会破坏 `python3 code/...` 的相对路径调用；技能目录名含连字符（`mathmodel-figure`）无法作为 Python 包名导入 |
| 在线 API 服务 | **暂不做** | 违背本地优先与「无运维」；且用户赛题数据出本地有合规与隐私顾虑 |
| 自建 agent 框架 | **明确不做** | 宿主（Claude Code / Codex / Trae 等）已提供运行时，重复造框架只会增加适配负担 |
| 全自动「1 小时出稿」 | **明确不做** | 见 §10 的合规与定位分析 |

## 三、潜在挑战与风险

| # | 风险 | 具体表现 | 缓解措施 |
|---|---|---|---|
| 1 | **赛道拥挤** | 已有 5000+ 星同类项目与 32 个被收录的公开项目，同质化严重 | 不追「全自动出稿」的军备竞赛；把差异化压在**确定性、可复现、可校验**（§10） |
| 2 | **赛事合规风险** | 各赛事对 AI 使用的规定不一；自动代写可能违规 | 坚守「机械正确性交给技能，建模判断留给人」；文档与自身定位明确为**提效与校验工具**，不承诺代写获奖 |
| 3 | **规范双写漂移** | 主技能 `SKILL.md` 与 `mathmodel-paper/SKILL.md` 存在同源条文，易不同步 | 确立单一权威：专项技能声明「规范以主技能为准」；索引类内容改为由注册表 + CI 校验 |
| 4 | **注册表漂移** | 新增模板需要同步多处清单 | 已收敛为「注册表一行 + 索引文档一行」；CI `manifest-consistency` 校验登记表 ↔ 文件系统 ↔ 索引文档 ↔ 版本号 ↔ README 徽章 |
| 5 | **Schema 与 docstring 双写** | JSON Schema 与脚本 docstring 描述同一契约 | 明确分工：Schema 是**机器校验权威**，docstring 保留人读说明；CI 校验示例与 Schema 一致 |
| 6 | **中文耦合** | 默认目录名、错误信息、图内文案为中文 | 代码层提供 `--lang {zh,en}`；内容层（模板文案、规范正文）不翻译，避免半吊子本地化 |
| 7 | **宿主碎片化** | 目前仅示范 Claude Code 安装 | 文档给出通用安装口径（复制技能目录到宿主的 skills 目录）；按实际反馈补宿主说明 |
| 8 | **单人维护带宽** | 评审与合并能力有限 | 用流程把「可自动判定」的部分交给 CI，人只评审**语义与创新性**（§7） |
| 9 | **内容质量参差** | 第三方模板可能语义错误（比字数超框严重得多） | 提交清单强制要求字数预算实测 + 语义约定说明；PR 模板逐项确认 |
| 10 | **过度工程** | 工具箱化容易滑向「抽象先行」 | 每项设施都要有**当下使用者**（CI、贡献者或用户）才做；本期已明确拒绝包化与在线服务 |

## 四、模块化组件架构规划

采用**三层模型**，层间只通过文件与 CLI 耦合：

```
┌─ 契约层（机器可读）──────────────────────────────────────────┐
│  code/tools/manifest.json（图表）                              │
│  code/templates/manifest.json（示意图）                        │
│  code/templates/schema/*.schema.json（5 份内容契约）            │
│  themes/theme.schema.json + themes/*.theme.json（配色契约）     │
└───────────────────────────────────────────────────────────────┘
              ▲ 读取注册与校验
┌─ 实现层（确定性渲染）─────────────────────────────────────────┐
│  图表：code/templates/make_*.py（20）  code/style/plot_style.py │
│  示意图：code/templates/*.py（5）      code/common.py           │
│  工具：render_template.py  validate_content.py                 │
│  工具：validate_theme.py                                       │
│  论文：paper.tex  word_postprocess.py  strip_invisible.py       │
└───────────────────────────────────────────────────────────────┘
              ▲ 被编排调用
┌─ 编排层（判断与流程）─────────────────────────────────────────┐
│  math-modeling-helper：六阶段编排 + 写作规范 + 自检 + 评分       │
└───────────────────────────────────────────────────────────────┘
```

**不可破的约束：技能目录自包含**。每个 `skills/<name>/` 必须能被单独复制到宿主的 skills 目录后独立工作。
这条约束直接排除了「共享一个跨技能 Python 包」的方案，也解释了为什么跨技能一致性要靠 **CI 校验**而不是靠 `import`。

**接口边界**：层间通信只有三种形式——①读注册表与 Schema；②调用 CLI 并以退出码判定；③读写约定路径的文件。
禁止跨层直接 import 实现细节。

**Phase 3 候选（需触发条件）**：若出现「第三方程序需要以库方式调用渲染器」的真实需求（而非假设），
再评估抽出可安装的命名空间包（届时需同时提供目录内相对路径的兼容层）。当前证据不足，不做。

## 五、数据模型标准化方案

### 5.1 命名与版本

| 项 | 规定 |
|---|---|
| 模板 id | kebab-case（如 `problem-flow`、`grouped-bar`），与脚本名的 snake_case 一一映射 |
| 契约版本 | 每个注册表带 `schema_version`（当前 `1.0`），Schema 用 `$schema` 声明 Draft 2020-12 |
| 项目版本 | 根 `VERSION` 单一来源；`CHANGELOG.md` 必须含该版本小节（CI 强制） |

### 5.2 路径解析规则（消除歧义）

首期实现中曾出现「`script` 相对谁」的歧义，已用**显式字段**消除：

- `script_dir`：模板脚本所在目录，相对**注册表所在目录**；
- 其余路径字段（`example`/`preview`/`schema`/`doc`）：一律相对**注册表所在目录**。

规则由注册表 `description` 写明，并由 CLI 与 CI 按同一逻辑解析。

### 5.3 内容契约的严格度取舍

- **必备字段**取自模板代码的事实行为：`need()` 调用或 `c['key']` 下标访问的字段才是必备，
  其余走 `.get(默认值)` 的字段为可选——契约不得比代码更严，否则会拒绝合法输入；
- **例外**：五带路线图要求 `band1..band5` 全部存在。代码对缺带走默认值，但缺带即残缺图，
  故在 Schema 中升为必备，并在 `description` 说明理由；
- **`additionalProperties: true`**：允许 `_comment` 等元信息与未来扩展字段，
  避免「加一个注释就校验失败」。契约约束的是**结构与取值**，不是字段封闭集。

### 5.4 兼容性规则

- `MINOR`：新增可选字段、新增模板、新增 Schema；
- `MAJOR`：移除既有 CLI 参数、移除注册表字段、**扩大**必备字段集合、收紧枚举取值；
- `PATCH`：文档、示例、错误信息与实现修复。

## 六、开放 API 接口设计方案

对技能集而言，「开放 API」= **三种可被外部依赖的接口面**，而非 HTTP 服务。

### 6.1 接口面一：CLI 契约（面向用户与 agent 宿主）

| 命令 | 关键参数 | 说明 |
|---|---|---|
| `code/tools/render_template.py <id\|别名\|中文片段>` | `--list`、`--list --json`、`--theme`、`--list-themes`、`--project`、`--overwrite`、`--lang` | 图表渲染（`--theme` 换配色，默认主题可省略） |
| `code/tools/render_template.py <id> <content.json>` | `-o/--out`、`--check`、`--list`、`--lang` | 示意图统一入口 |
| `code/tools/validate_content.py <id> <content.json>` | `--all`、`--schemas`、`--lang` | 内容契约校验 |
| `code/tools/validate_theme.py [<主题文件>...]` | `--all`、`--list`、`--lang` | 主题契约校验 |
| `code/word_postprocess.py [paper.docx]` | — | Word 版式微调 |
| `code/strip_invisible.py <files...>` | `--clean`、`--no-backup` | 不可见字符清理 |

**退出码语义统一**：`0` 成功 / `1` 校验或渲染失败 / `2` 用法或环境错误。
这是让脚本能被其他程序编排的关键——机器只认退出码。

### 6.2 接口面二：清单与 Schema（面向程序与第三方）

`manifest.json` 提供 `--list --json` 的等价物：id、脚本、标题、分组/画布、别名与中文提示、示例与预览路径、署名。
第三方据此可**枚举能力、生成文档、做自己的前端**，无需读源码。

`themes/theme.schema.json` 是第二类数据契约：配色按「身份 / 基准 / 方向 / 层级」四类角色声明，
渲染器把所选主题写入工作区 `scripts/theme.json`，样式模块按「同目录 → 内置默认 → 内置兜底」读取。
于是**配色成为可替换的数据**：第三方可发布自己的主题、程序可批量切换、CI 可校验其结构合法性。
已知边界：主题只覆盖共用样式模块的 9 个图表模板与按其自绘的图，其余 11 个模板与 5 个示意图的配色
仍写在各自脚本头部（属实现细节，可在工作区副本中改，但不属契约层）。

### 6.3 接口面三：Python 可 import 函数（面向同仓脚本）

`resolve_template()`、`list/load_manifest()`、`validate()`、`script_path()` 等以模块函数暴露，
供同技能内脚本复用（`validate_content.py` 即通过 `sys.path` 注入复用统一入口的解析逻辑）。
**不以「可 pip 安装」为前提**，故不承诺包级 API 稳定性。

### 6.4 接口稳定性分级

| 级别 | 范围 | 承诺 |
|---|---|---|
| **Stable** | 上述 CLI 参数与退出码、注册表字段、主题契约字段（`roles`/`cmaps` 结构与字段名）、`schema_version` 语义 | 破坏性变更须升 `MAJOR` 并写入 CHANGELOG |
| **Experimental** | `--lang` 的具体文案、`--json` 输出的字段顺序、错误信息措辞、默认主题的具体色值（属内容） | 可随时调整，不视为破坏性 |
| **Internal** | 模板脚本内部的几何常量、`common.py`/`plot_style.py` 的基元签名 | 无承诺，仅限仓内使用 |

## 七、第三方开发者合作机制

### 7.1 贡献路径（按成本从低到高）

1. **新增模板**：写脚本 → 加 `docs/templates/<id>.md`（含逐槽字数预算与语义约定）→ 加 `example.json` 与 `preview.png`
   → **注册表加一行**。CI 自动校验其余一致性，**无需改动 CLI、CI 与索引文档**；
2. **改进既有模板**：改脚本 → 重渲预览 → 更新字数预算；
3. **文档与示例**：修正、补充场景；
4. **缺陷报告**：附最小复现（内容 JSON + 命令 + 期望）。

### 7.2 机器管什么、人管什么（关键分工）

| 由 CI 自动判定（无需人看） | 只能由人评审 |
|---|---|
| 语法、渲染成功、产物非空 | 槽位**语义**是否正确（并列/汇流/对比放错比字数超框严重得多） |
| 注册表 ↔ 文件系统 ↔ 索引文档一致性 | 文案是否忠于题目材料（禁止编造） |
| Schema 合法性、示例合规 | 字数预算是否经实测（不允许手估） |
| 版本号 ↔ CHANGELOG ↔ README 徽章 | 是否值得做成模板（一次性图型直接手写更快） |

这条分工是**单人可维护**的前提：机器吞掉机械校验，人只花时间在判断上。

### 7.3 评审口径

- 必须项：CI 全绿；`example.json` 填满真实内容（不接受占位符）；文档含字数预算与语义约定；
- 加分项：模板能覆盖一类反复出现的图型；提供边界数量的压力配置验证；
- 拒收项：编造数据或文献；语义标注错误；仅改观感但破坏既有调用契约。

### 7.4 署名与许可

贡献即同意以 Apache-2.0 分发；模板作者在注册表 `author` 字段永久署名（见 §8）。

## 八、用户贡献激励体系

开源项目的激励不必是金钱，**稀缺的是可见性与署名**。设计原则：**不做空头承诺、不建空文件**。

| 贡献等级 | 具体行为 | 可见回报（均已落地或本期落地） |
|---|---|---|
| L1 缺陷报告 | 附最小复现 | CHANGELOG「修复」条目 + Release notes 致谢 |
| L2 文档与示例 | 修正说明、补充示例 | 同上 |
| L3 模板贡献 | 新增可用模板 | 注册表 `author` 字段**永久署名**；模板目录中与官方模板并列展示 |
| L4 长期维护 | 持续评审与治理 | 在 §11 的路线图中列为共同维护者 |

配套机制：`CHANGELOG.md` 按变更类型归集（新增/变更/修复/文档），使贡献在历史上可检索；
`release.yml` 从 CHANGELOG 生成 Release notes，发布即致谢。

**明确不做的**：不创建空的 `CONTRIBUTORS.md`（无内容即无激励，反而显得敷衍）；
不承诺积分、代币或排名（无履约能力）。

## 九、版本迭代策略

### 9.1 节奏与版本

- 语义化版本，`VERSION` 为单一来源；
- 本方案对应的版本为 **`1.1.0`**（向后兼容的能力新增）；
- 发布动作：打 `v*` 标签 → `release.yml` 校验「标签 == VERSION == CHANGELOG 小节」→ 生成 Release notes。

### 9.2 兼容性承诺

| 面 | 承诺 |
|---|---|
| CLI 参数与退出码 | 移除或改变语义须升 `MAJOR` |
| 注册表字段 | 移除字段须升 `MAJOR`；新增可选字段属 `MINOR` |
| 内容 Schema | 扩大必备字段集合或收紧枚举属 `MAJOR` |
| 产物格式与路径 | 视为 Stable（用户脚本可能依赖） |

### 9.3 环境与依赖

- Python：CI 固定 3.12 作为**最低验证版本**；文档中的自测版本与本项保持一致（已修正此前 3.12 / 3.14 表述不一）；
- 可选依赖：`jsonschema`（严格校验，缺失时降级为内置最小校验器）；`pymupdf` 仅 PDF 清理模式需要；
- 外部工具：`xelatex`、`pandoc`。模板骨架的西文字体已改为**带回退探测**（Times New Roman → TeX Gyre Termes），
  CI 不再需要打补丁。

### 10.2 竞争格局判断

- **赛道已拥挤且同质化**：主流路线是「多智能体 + LLM 全自动生产」，比拼的是模板数量、支持的赛事数、交付速度；
- **隐含代价被普遍低估**：全自动路线难以证明**数字可追溯**（论文里的每个数能否追回脚本产物），
  而这恰是评审与合规最在意的部分；
- **生态层已出现第三方评估框架**（上表末行），其评估维度（证据链、可复现性、许可证、人机边界）
  与全自动路线的薄弱点高度重合。

### 10.3 本项目的差异化（四项可被验证的优势）

1. **确定性与可复现**：示意图由 content JSON 驱动、图表模板自带种子化数据，任何产物都能重渲与二次修改；
   对照的是「LLM 每次生成不同结果、无法复现」的痛点；
2. **机器化质量门禁**：字数超框即非零退出、渲染前逐槽量中文字宽、注册表与文档一致性 CI 校验、
   论文自检清单与百分制评分——把「靠眼看」的部分尽量变成可判定；
3. **反造假约束**：禁止编造文献与数据、模拟数据不得声称复现真实结果、论文数字须可追溯；
4. **交付一致性**：PDF 与 Word 双产物 + 版式一致性核对 + **零宽/不可见字符清理**（含 PDF 层 ToUnicode 反查），
   这是当前同类项目普遍未覆盖的最后一公里。

**生态位选择**：不做与全自动平台正面竞争的「代写」，而做**可被任何宿主与流程调用的确定性工具箱层**——
把图、表、流程示意、排版与交付校验做成别人敢依赖的组件。

### 10.4 合规立场

赛事对 AI 使用的规定不一，且逐年收紧。本项目明确以**提效与校验**为定位：
机械正确性（可复现、不裁切、数字可追溯、格式过检）交给技能，**方法选型、结果解释与创新点表述留给人**。
这不是能力不足的妥协，而是**可长期存续的定位**——它不依赖赛事规则对代写的容忍度。

### 11.1 三期路线

| **Phase 2** | 生态与分布 | 多宿主安装说明；向社区索引目录（如前述资源目录）登记；模板贡献者案例；英文文档与 Schema 字段说明对齐；把主题控制扩展到其余 11 个图表模板（消除配色双轨） | 待启动 |
| **Phase 3** | 开放组件化 | 按真实需求评估：可安装命名空间包 / 被第三方程序嵌入的稳定 Python API；**触发条件**：出现明确的第三方程序化调用需求 | 条件触发 |

### 11.2 首期成果评估标准（KPI）

| 指标 | 基线（升级前） | 首期目标 | 当前实测 | 度量方式 |
|---|---|---|---|---|
| 新增模板需手动改动的位置数（不含新脚本与示例本身） | 4 处（清单/索引文档/SKILL/CI 数量） | **2 处**（注册表一行 + 索引文档一行） | 2 处（CLI、CI、版本号均无需改动） | 按 CONTRIBUTING 实操计数 |

| CI 中的硬编码模板数量断言 | 4 处 | **0 处** | 0 处 | 检索 `-ne 20` 与固定五元组 |
| 解析行为回归 | — | 迁移不改变任何解析结果 | 81 用例 0 失败 | 对照迁移前字典逐项比对 |
| 治理文档完备度 | 无 | CONTRIBUTING×2、PR/Issue 模板、VERSION、CHANGELOG、release 流程 | 全部具备 | 文件存在性 + CI 校验 |

### 11.3 评估节奏

- 每次合并：由 CI 自动核对上表第 2、3、5、7 项（机器指标）；
- 每次发版：由 `release.yml` 核对版本三处一致（`VERSION`、标签、CHANGELOG）；
- 每期结束：人工复核第 1、4 项（需实操与对比，机器无法替代）。
